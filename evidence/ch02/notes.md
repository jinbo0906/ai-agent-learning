我现在把上下文理解为 Agent 的“信息供给”：Harness 决定每轮向模型呈现哪些指令、历史、工具和环境状态。把信息全部放进去未必更好；遗漏关键状态、错误的角色格式或无序的规则，同样会让决策退化。

## 必答问题

### Q1. 为什么滑动窗口可能让 Agent 重复调用工具？

旧工具结果滑出窗口后，模型只看到“还需要这个信息”，却看不到“已经查过及查到了什么”，于是可能再次调用。长度控制还应配合可回查的事件记录；调用前检查工具名、参数和数据版本，确认结果仍有效时复用。见[思考题 1](./reading-notes.md#思考题)。

### Q2. 如何在不破坏稳定前缀的前提下控制长期轨迹？

保持系统规则和核心工具的序列稳定，把新增观察追加到后部。完整轨迹与原始结果存于外部，模型只接收近期交互、关键状态和必要的原文引用。阶段性压缩旧消息会使替换点之后的缓存重算，所以应在检查点集中进行；它不能保证整段历史永远命中缓存。见[思考题 1、9](./reading-notes.md#思考题)。

### Q3. Prompt 的多人维护为什么会产生“熵增”？

维护者通常只为眼前案例追加规则，久而久之会出现作用域重叠、优先级不明和相互矛盾的要求。把规则分模块、明确适用条件与责任人，以固定顺序生成提示词；改动时回放同一组任务，观察关键约束是否退化。见[思考题 5](./reading-notes.md#思考题)。

### Q4. 如果模型不知道自己不知道什么，Skill 如何被正确触发？

除了模型自主选择，还应提供用户显式指定、按文件类型或任务类型给出候选、失败后重新查询目录等入口。分别记录漏触发与误触发，而不是只看 Skill 是否被读过；读取后是否遵从，还要用最终任务结果检验。见[思考题 7、8](./reading-notes.md#思考题)。

### Q5. 哪些信息应保留原文，哪些适合摘要，哪些应隔离到子 Agent？

精确 ID、用户约束、可争议事实、失败原因与出处应保留原文或可靠回查入口；冗长而重复的工具输出可按当前任务摘要，但原始快照仍需留存。大规模搜索等相对独立、会制造大量中间噪声的工作适合交给子 Agent，仅把结论和定位信息带回主上下文。见[思考题 3、6](./reading-notes.md#思考题)。

## 一句话核心主张

上下文工程的关键是让模型在决策时得到**足够且可核实的信息**，同时让原始证据可回查、稳定前缀可复用；上下文越长并不自动意味着决策越好。
