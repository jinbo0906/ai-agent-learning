# 第一部分 · Attest 是什么

## 1.1 一句话

**把"我学会了"变成"这里有证据"。**

它不是打卡工具，不统计你读了多少页、提交了多少次。它只做一件事：
在你声称掌握某一章时，检查这个声称背后有没有可验证的东西撑着。

## 1.2 它要防的四个真实问题

这是理解整个系统的钥匙——**每一个机制都对应一个具体的失效模式**，
没有对应失效模式的机制（比如签名、哈希绑定）一律不做。

| | 失效模式 | 为什么危险 | Attest 的机制 |
| --- | --- | --- | --- |
| **T1** | **AI 代写笔记与文章** | 产出看起来完美，但没进脑子。这是 2026 年学习的头号问题 | **个性化答辩**：追问必须锚定你提交里的**具体数字、具体代码选择、具体主张**。能不看你的提交就回答的问题是无效问题。再加 D+21 复述——AI 写的东西三周后你解释不了 |
| **T2** | **实验只跑通不分析** | 有 `summary.json`，但报告里的结论和数据没关系 | **数字接地检查**：报告和文章里出现的每个数字，必须能在 `summary.json` 里定位到。对不上直接 `needs_work` |
| **T3** | **学完就忘** | 十八周后前六章全还回去了 | **间隔复习** D+2 / D+7 / D+21 + **保持率** = 复习分 ÷ 首评分 |
| **T4** | **自欺（自评远高于真实水平）** | 你以为懂了，所以不再深究 | **校准误差** = `mean(\|自评 − Judge评\|)`。每章先自评再看 Judge 分数，追踪差值趋势 |

反过来，**明确不防的**：篡改分数文件（你是唯一用户，为防自己作弊上密码学是负收益），
学习者代码攻击评估系统（代码是你自己写的）。

> T4 的校准误差是这套设计里最独特的一环。它衡量的不是"你会多少"，
> 而是"**你知不知道自己会不会**"。元认知准确度比分数本身更能预测长期学习效果，
> 而且几乎没有学习产品在测这个。

## 1.3 三个抽象

系统的可复用性取决于内核是否与"AI Agent Book"无关。三个抽象都无关：

```
      ┌──────────────────────────────────────────────────────┐
      │  ① 课程规格  attest/curriculum.yml                    │
      │     十章的：目标 / 必答问题 / 实验要求 / 修正 /        │
      │             文章命题 / 通过标准 / Attest 里程碑        │
      │     ← 换一本书，只换这个文件                          │
      └───────────────────────┬──────────────────────────────┘
                              │ attest start
                              ▼
      ┌──────────────────────────────────────────────────────┐
      │  ③ 证据包  evidence/chNN/                             │
      │     notes / report / article / quiz / defense / lab   │
      │     ← 目录约定，与学科无关                            │
      └───────────────────────┬──────────────────────────────┘
                              │ attest check / grade / defend
                              ▼
      ┌──────────────────────────────────────────────────────┐
      │  ② 评分卡  attest/rubrics/engineering-book.yml        │
      │     四维 + 权重 + 锚点 + 反模式 + 答辩协议            │
      │     ← 与学科无关，可复用可分享                        │
      └──────────────────────────────────────────────────────┘
```

引擎的六步 `start → check → quiz → grade → defend → review` 同样与内容无关。
**换一门课 = 写一份 curriculum.yml + 选一张 rubric。** 这是产品化的地基。

## 1.4 三层评估：为什么这么分层

```
第 1 层  确定性检查   本地 · <2 秒 · 零成本 · 随时可跑
         能用代码判定的全部放这里：必填小节非空、必答问题已作答、
         数字接地、复现命令、密钥扫描
         ↓ 失败就停，**不调用 LLM**

第 2 层  语义评分     本地调 API · ~30 秒 · ~0.3 元
         只有代码判不了的才交给 LLM：概念准确性、因果推理、
         场景迁移、证据与结论是否匹配

第 3 层  个性化答辩   终端对话 · ~10 分钟 · 你必须在场
         LLM 也判不了的：这些东西是不是你自己想出来的
```

**分层的意义在于成本和确定性的匹配**：

- 第 1 层零成本可重复 → 你会在**写作过程中**反复跑它，而不是写完才发现结构不对。
  这是本地优先带来的最大收益，它把质检**前移**了。
- 第 1 层失败不调 LLM → 结构没写完就去打分是浪费钱，而且反馈还不准。
- 第 3 层必须你在场 → 这是全套体系里唯一不能自动化的部分，也是唯一真正防 AI 代写的部分。

## 1.5 判定与门控

四维评分（与原方案一致，这部分设计是对的）：

| 维度 | 权重 | 主要证据来源 |
| --- | ---: | --- |
| 概念理解 | 25 | `notes.md`、`quiz.md#Part A` |
| 场景与代码 | 30 | `quiz.md#Part B`、`lab/` |
| 实验证据 | 25 | `report.md`、`summary.json`、`quiz.md#Part C` |
| 费曼讲解与反思 | 20 | `quiz.md#Part D`、`defense.md` |

**判定只有 3 条**（原方案有 8 条，状态有 6 种），按顺序：

```
① 确定性检查失败        → needs_work（不调 LLM）
② 答辩未完成            → needs_work
③ 总分 ≥80 且每维 ≥60%  → done；否则 needs_work

基础设施错误（API 超时、返回非法 JSON）→ 不写分数，只记 last_error，
                                          保留上一次有效结果
```

最后一条很重要：**学习失败和基础设施故障必须分开**。API 挂了不该让你的分数变低。

完成级别是三级而不是一票否决：

| 级别 | 条件 |
| --- | --- |
| 🥉 铜 | 十章齐套，≥8 章 done，平均 ≥75 |
| 🥈 银 | 十章 done，平均 ≥80，十篇文章过发布门，Attest 到 v2 |
| 🥇 金 | 银 + 3 旗舰 + v3 + 总复盘 + D+21 保持率 ≥0.8 |

第 7 章卡住（很可能，它要 GPU）不会让整个 18 周判定失败——你仍然能拿银，
并且**清楚地知道差在哪**。

## 1.6 两个刻意的取舍

**取舍一：本地 CLI，不是 GitHub Actions。**
反馈延迟从 3–8 分钟降到 <2 秒；答辩从"2 次 push + 2 次等 CI + 手工搬哈希"降到一次终端对话；
笔记保持私有，所以你**可以诚实地写"我不懂"**——而诚实度是这套方法全部价值的来源。
Git 仍然用，但它是**账本**（版本化证据，`git diff` 就是认知变化），不是**流水线**。

**取舍二：没有签名和哈希绑定。**
安全强度按真实威胁配置。签名防的是"篡改分数"，但你是唯一用户；
而它对真正的风险（AI 代写）完全无效——AI 写的内容照样能被合法签名。
省下的工程量（原方案估算 150–300 小时）全部投到答辩加强和校准误差上。

## 2.2 你会碰到的文件，按频率排

| 频率 | 文件 | 你在做什么 |
| --- | --- | --- |
| **每天** | `evidence/chNN/*.md` | 写笔记、报告、文章、测试 |
| **每天** | `evidence/chNN/lab/` | 跑实验、改代码、存结果 |
| **每周** | `attest/src/attest/*.py` | 把本章能力装进系统（v0→v3） |
| **每周** | `progress/weekly/week-NN.md` | 周复盘 |
| **偶尔** | `attest/curriculum.yml` | 发现某章要求不合适，微调 |
| **很少** | `attest/rubrics/*.yml` | 改评分标准（改了必须回放校准集） |
| **只读** | `../chapter*/`、`../book/` | 书稿和原始实验（**只读基线，不改**） |

## 2.3 `curriculum.yml` —— 单一事实源

每章一条记录，14 个字段。最重要的四个：

```yaml
- id: ch01
  must_answer:          # ← 会被写进 notes.md，是本章的核心检验点
    - 模型很强时，为什么 Harness 的价值反而可能增加？
    - ...
  default_lab:          # ← attest snapshot 从这里读，复制到 lab/<项目名>/
    path: chapter1/context
    status: ok          # ok | warn | fix
  lab_requirements:     # ← 会被写进 report.md 的勾选清单
    - 固定模型、任务集、采样参数、最大步数
    - ...
  attest_milestone:     # ← 本章学完要把什么能力装进系统
    version: v0
    what: Agent 循环骨架 —— 读证据（工具）→ 调 LLM 判分（模型）→ 写结果（工具）
```

第 6/7/9 章多一个 `fix` 字段，记录默认实验与原方案要求的**事实冲突**及处理办法。
这些内容会被 `attest start` 直接渲染进 `report.md`，所以你不会踩坑。

**什么时候改它**：跑到一半发现某章的实验要求不现实（比如 API 太贵、数据集构造超时）。
改完重跑 `attest start N --force` 会覆盖模板部分——**但会覆盖你已写的内容**，所以
改要求时通常手工同步到 `report.md` 更安全。

## 2.4 `rubrics/engineering-book.yml` —— 评分卡

四个维度，每个含：权重、及格线、证据来源、子维度、**锚点**（5/3/1 分各长什么样）、
**反模式**（什么写法直接扣分）。

反模式这部分特别值得读，它就是"哪些是自欺"的清单，例如：

- 概念维度：用术语解释术语、把书里的类比当结论
- 场景维度：把书里的示例代码改个变量名当新方案、只写 happy path
- 实验维度：**报告里的数字在 `summary.json` 里找不到**、只保留成功轨迹、无保留集
- 讲解维度：**答辩回答与提交内容无关（典型的 AI 代写信号）**、"我学到了很多"式反思

写作时对着反模式自查一遍，比事后被 Judge 扣分效率高得多。

## 2.5 六类产出各自的角色

| 文件 | 性质 | 核心约束 | 谁会看 |
| --- | --- | --- | --- |
| `notes.md` | **私有** | 必须诚实。允许并鼓励写"我不懂" | 只有你和 Judge |
| `report.md` | 内部 | **每个数字必须在 `summary.json` 里找得到** | 你和 Judge |
| `article.md` | **公开** | 一个可争辩的主张 + 自己的实验数据 + 失败边界 | 所有人（过发布门后） |
| `quiz.md` | 内部 | 开卷，但必须引用自己的代码与实验 | 你和 Judge |
| `defense.md` | 内部 | 追问必须锚定你的具体内容；回答 ≥80 字 | 你和 Judge |
| `lab/` | 内部 | 快照 + 基线 + 一个变量 + 成功和失败轨迹 | 你和第三方复现 |

**为什么笔记要私有**：如果知道低分和"我不理解 X"会被公开，你写笔记时必然会美化。
而这套方法的全部价值恰恰来自诚实记录不懂的地方。只有 `article.md` 对外。

### 必填 vs 可选（重要）

**模板是笔记本，不是必须填满的表格。**

每个文件里 `<!-- attest:optional-below -->` 分界线**以上**的是必填，
以下（折叠块里的角度提示）全部可选，`attest check` 不管。

| 文件 | 必填（就这些） |
| --- | --- |
| `notes.md` | 读之前我怎么想 · **必答问题 Q1–Q5** · 一句话核心主张 · 我还不懂的 |
| `report.md` | 我跑了什么 · 结果 · 数据说明了什么 · 哪里没成 |
| `article.md` | 我的主张 · 我原来怎么想 · 证据 · 什么情况下不成立 |
| `quiz.md` | 自评 · Part A–D |
| `defense.md` | 两个追问 + 回答 + 我发现的漏洞 |

早期版本每个文件有十几个必填 H2（工程权衡表、反例四问、与既有经验的连接、
证据索引、AI 辅助披露……）。那套是从「可审计的自动评审」需求搬来的，
对个人学习是纯负担——**为了填格子会逼你去抄书，那是负价值**。已经砍掉。

保留下来的唯一强约束是 **`summary.json` 数字接地**：它是机制性的
（防"只跑通不分析"），不是格式要求。

**必答问题答不出来，写"我不确定，因为……"就行。** 那是真实的学习状态，
是有用的数据。空着才是问题。

## 2.6 代码模块与扩展点

| 模块 | 行数 | 职责 | 你会怎么改它 |
| --- | ---: | --- | --- |
| `spec.py` | ~70 | 加载 curriculum + rubric，路径常量，章节 ID 归一化 | 基本不动 |
| `scaffold.py` | ~330 | `start`（渲染模板）+ `snapshot`（复制实验） | 加新的模板变量时改 `_vars()` |
| `check.py` | ~250 | 第 1 层七项检查 | **Day 3 实现 `check_numbers_grounded`**；v2 加复现执行 |
| `llm.py` | ~200 | OpenAI 兼容客户端 + 记账 + 预算护栏 + `ping` | 加流式、加缓存时改 |
| `__main__.py` | ~150 | 命令分发 + `status` 看板 | **每加一个命令改这里** |

`llm.py` 刻意做得很薄——**它没有任何评分逻辑**。Judge 怎么设计（prompt 组装、
rubric 应用、证据引用、追问生成）是第 1/2/6 章的学习内容，由你写在 `grade.py` / `defend.py` 里。

给你这一层，是因为写 HTTP 客户端没有学习价值，不该占用你的 7.5 小时。

用法：

```python
from attest.llm import chat

r = chat(
    [{"role": "system", "content": "..."}, {"role": "user", "content": "..."}],
    tag="grade:ch01",      # 记账标签，看板按它统计每章成本
    json_mode=True,        # 要求返回 JSON object
)
result = r.json()          # 自动剥 ```json 围栏并解析
print(r.cost_cny, r.latency_s, r.prompt_tokens)
```

失败时抛 `LLMError`（基础设施错误，你的 `grade` 应该捕获它并只写 `last_error`，
不动分数），预算超了抛 `BudgetExceeded`。

# 第三部分 · 一章的完整生命周期

这是最实用的一节。**每一章都走完全相同的五步**，走熟了之后不需要再看文档。

## 3.1 五步总览

| 步 | 名称 | 命令 | 耗时 | 产出 |
| --- | --- | --- | ---: | --- |
| ① | 定标 | `make start CH=N` + `make snapshot CH=N` | 5 min | 证据包 + 本章简报 |
| ② | 学做 | 读书 + 跑实验（随时 `make check CH=N`） | 5.5 h | `notes.md`、`lab/`、`summary.json` |
| ③ | 表达 | 写报告和文章 | 2.5 h | `report.md`、`article.md` |
| ④ | 验收 | `quiz` → `selfscore` → `grade` → `defend` | 1.5 h | `quiz.md`、`defense.md`、分数 |
| ⑤ | 沉淀 | 装进 Attest + 周复盘 + 排复习 | 1.5 h | 系统 vN + `week-NN.md` |
| | | | **~11 h** | 分摊到 1.5 周 = 7.3 h/周 |

## 3.2 ① 定标（5 分钟）

```bash
make start CH=1        # 或 python -m attest start 1
make snapshot CH=1
```

`start` 会做三件事：

1. **打印本章简报**——目标、5 个必答问题、默认实验、Attest 里程碑、必须连接的前置章节。
   花两分钟读完它，这决定了你这一章要往哪儿使劲。
2. **生成六类产出的骨架**，且**已经填好了本章特有的内容**：
   - `notes.md` 里已有本章的 5 个必答问题
   - `report.md` 里已有本章的实验要求勾选清单
   - `article.md` 里已有本章的文章命题和必须包含项
   - `quiz.md` 里已有本章的锚点题
   - 第 6/7/9 章的 `report.md` 里已有实验修正方案
3. **初始化 `.attest/state.json`**（状态 `draft`）

`snapshot` 把书里的实验复制到 `lab/<项目名>/`，并写 `provenance.json` 记录来源。
一章可以有多个实验（第 1 章 4 个、第 3 章 13 个、第 7 章 16 个），所以按项目名分目录：
`attest snapshot 1 web-search-agent` 再加一个，`attest snapshot 1 --all` 取全部。

> **为什么要快照而不是直接改书里的目录**：书里的目录是只读基线。
> 快照之后，`git diff` 就能看出你到底改了什么——这是"原创深改"的证据。
> 直接改原目录的话，你的改动和书的原始代码就混在一起了。

## 3.3 ② 学做（5.5 小时）

**读书（按章 1.5–3 h）**：先通读一遍标记疑问，再围绕必答问题精读。
边读边填 `notes.md`，尤其是「学习前理解」——**这一节必须在读之前或刚读完时写**，
等学完了再回头写，你会不自觉地写成"我早就知道"。

**跑实验（~3 h）**：

```bash
cd evidence/ch01/lab/context
cp ../../../../.env .env          # 或按项目 README 配置
python main.py --help
```

三条铁律：

1. **先跑基线，再改变量。** 而且**一次只改一个**。同时改两个的实验，结论不可信。
2. **结果必须落到 `lab/results/summary.json`。** 这是整个证据体系的锚点——
   报告和文章里的每个数字都要在它里面找得到。项目本身如果不输出这个文件，
   你自己写个小脚本把结果汇总进去。
3. **保存一条成功轨迹和一条失败轨迹。** 只有成功案例的实验报告不通过。
   失败轨迹往往是文章里最有价值的部分。

**随时跑 check**：

```bash
make check CH=1
```

<2 秒，零成本。**它的失败清单就是你的待办清单**（见 3.7）。

## 3.4 ③ 表达（2.5 小时）

**`report.md`**：把实验讲清楚。重点在三节——
「结论与适用边界」（数据支持什么、**不**支持什么）、
「失败案例」（至少一个）、「复现」（第三方能不能从这个目录跑起来）。

**`article.md`**：这是唯一对外的产出。它和报告的区别是：
报告回答"我做了什么"，文章回答"**我认为什么，凭什么**"。

一篇合格的文章有一个**可争辩的主张**。判断标准很简单：
如果没有人可能不同意你的标题，那它就不是主张，是摘要。

> 主张从哪来？**从实验里出乎意料的那个数据来。**
> 如果实验结果全在预料之中，说明变量选错了，换一个再跑。

## 3.5 ④ 验收（1.5 小时）

```bash
python -m attest quiz 1        # 生成本章测试（Part B 场景题）
# ... 做题，填 quiz.md ...
python -m attest selfscore 1   # 先自评！在看 Judge 分数之前
python -m attest grade 1       # 四维评分
python -m attest defend 1      # 2 个追问，终端作答
```

**顺序不能变**。`selfscore` 必须在 `grade` 之前——否则校准误差就是假的，
你会不自觉地往 Judge 的分数上靠。

答辩是这一步的核心。它会读你的提交，生成两个锚定你**具体内容**的追问，例如：

> 你在 `report.md` 的结果表里把成功率从 0.54 提升到 0.82 归因于保留工具结果，
> 但同一组配置的平均步数也从 9.1 降到 6.3。如何排除"步数减少导致出错机会变少"
> 这个混杂因素？

这种问题你没法预先准备，也没法让 AI 替你答——因为答案必须引用你自己的数据。
**如果两个问题你都答得很顺，说明问题出得太浅，重新生成。**

## 3.6 ⑤ 沉淀（1.5 小时）

**装进 Attest**：本章的 `attest_milestone` 说了要装什么。这一步是这套设计的精髓——
你不是"做了个 demo"，而是把这一章的能力装进一个**你每天都在用**的系统。
好不好用，你骗不了自己。

**周复盘**：`progress/weekly/week-NN.md`。重点填三处——
分数与校准误差表、「最值得保留的失败」、旗舰章信号表（第 6 周要用）。

**排复习**：章节 `done` 后自动排 D+2 / D+7 / D+21。

## 3.7 怎么读 check 的输出

`check` 按五步循环分组，**只展开你当前那一步**，后面的明确标着"先别管"：

```

  ────────────────────────────────────────────
  ① 读书   ◐ 进行中 —— 还差 8 项
           · notes.md · Q1. 模型很强时，为什么 Harness 的价值反而可能增加？
           · notes.md · Q2. Agent 和普通 LLM 调用的边界是什么？

           · notes.md · 读之前我怎么想

  ② 实验   ○ 未开始（4 项）  ⟵ 先别管

**读法**：这不是"你做错了"，这是**今天的待办**。只看展开的那一步，
其他的做到那一步再说。想一次看全部：`attest check 1 --all`。

草稿状态全红是正常的。全绿了才值得去 `grade`——结构没写完就打分是浪费钱，
反馈也不准。

## 4.1 为什么不替你写

因为**这就是学习内容本身**。

- `quiz` 的核心是"如何组装上下文让出题有区分度"——这是第 2 章。
- Judge 的可信度问题——这是第 6 章的校准。

如果我替你写完，你会得到一个能跑的工具和零收获。而且**你会不知道它什么时候不可信**。

## 4.2 实现顺序

```
Day 3     check_numbers_grounded    ~60 行   测试已写好
ch1 周内  selfscore                 ~40 行   纯交互，最简单，先做它找手感
ch1 周内  grade                     ~150 行  ← v0 核心

ch3 后    review                    ~150 行

## 4.3 设计 brief

### `attest selfscore N`（~40 行）

- **输入**：终端交互
- **输出**：写 `.attest/state.json` 的 `self_score`
- **做什么**：依次问四个维度的分数（各自满分 25/30/25/20），拒绝在 `judge_score`
  已存在时覆盖（否则校准误差作废）
- **验收**：跑两次，第二次应拒绝并提示"已评分，重评请先清空 judge_score"

### `attest grade N`（~150 行）← v0 核心

- **输入**：`notes.md` + `report.md` + `article.md` + `quiz.md` + `summary.json`
  + rubric + curriculum 的本章条目
- **输出**：`.attest/state.json` 的 `judge_score` / `total` / `calibration_error`，
  以及一份 `evaluation.json`（分数 + 逐维理由 + 证据引用）
- **五个设计要点**：
  1. **先跑 `check`**，FAIL 就直接返回 `needs_work`，不调 LLM（判定第 1 条）
  2. Judge 必须输出结构化 JSON：`chat(..., json_mode=True)` + `r.json()`
  3. **每个维度必须给出至少一条 `{path, location}` 证据**，否则重试一次；
     两次都给不出就说明 Judge 在编，标记 `needs_review`
  4. 计算 `calibration_error = mean(|self − judge|)`，写回 state
  5. 捕获 `LLMError` → 只写 `last_error`，**不动已有分数**（基础设施错误 ≠ 学习结果）
- **验收**：
  - 对一份故意写得很空泛的 `notes.md` 打低分，对一份扎实的打高分
  - **同一输入连跑两次，总分差 <8**（这就是 v2.5 要正式测的自洽性）
  - 断网时不改变已有分数

### `attest defend N`（~120 行）← 防 AI 代写的关键

- **流程**：
  ```
  读提交 → LLM 生成 2 个追问 → 终端 input() 收答案 → 第二次调用只评分
  → 写 defense.md + 更新 state 的 teachback 维度
  ```
- **四个设计要点**：
  1. **问题必须锚定具体内容**。加一条自检：如果生成的问题里不含任何来自提交的
     具体词（数字、文件名、配置名、指标名），就重新生成。这是全套机制里最重要的一行代码
  2. 回答 <80 个非空白字符直接拒绝
  3. **第二次调用只评分，不允许再出新问题**（否则会无限追问）
  4. 只更新 `teachback` 维度，不动其他三维
- **验收**：拿一段明显是 AI 泛泛而谈的回答喂进去，`teachback` 应该显著低于
  你自己写的、引用了具体数字的回答

### `attest quiz N`（~80 行）

- **输入**：curriculum 的 `quiz_anchors` + 正文片段 + 你的 `notes.md` + 历史错题
- **输出**：填充 `quiz.md` 的 Part B 场景题（Part A 锚点题模板里已有）
- **要点**：场景要换业务领域、换数据规模、换资源约束，降低背答案的价值

### `attest review`（~150 行）

- 读 `progress/review-queue.yml`，列出到期项，生成题目，收答案，算保持率，
  更新 `next_review` 和 `consecutive_correct`
- **要点**：同一错误连续两次出现时，不再生成相似题，而是要求补一个最小实验或反例解释

### `attest board`（~250 行）← v2.5

- 生成 `progress/board.html`：章节状态、四维雷达、**校准误差趋势**、保持率、
  证据密度、复现率、返工轮数、累计成本
- 同期做 **Judge 校准**：用前五章历史评分建校准集，测自洽性、位置偏差、长度偏差
- **这一步之前，你没有任何理由相信 Judge 给的分数**

## 4.4 v0 → v3 与章节的对应

| 版本 | 时点 | 装什么 | 用哪一章的能力 |
| --- | --- | --- | --- |
| **v0** | ch1 后 | `grade`/`defend` 的 Agent 循环骨架：读证据（工具）→ 判分（模型）→ 写结果（工具）；终止、重试、预算 | 第 1 章 Harness |
| **v0.5** | ch2 后 | 分层上下文：稳定前缀（rubric + 规格）+ 动态部分（本章证据）。**实测缓存命中的成本下降，这组数据直接进你的第 2 章文章** | 第 2 章 KV Cache |

| **v1.5** | ch4 后 | 工具化 + 主动发现。**用自己的系统做本章实验**：全量注入 vs 按需发现的真实 token 对比 | 第 4 章 工具设计 |
| **v2** | ch5 后 | 复现检查器：沙箱内执行 `reproduce.json`、跑测试、比对 `summary.json` | 第 5 章 生成—执行—验证 |

## 5.2 第 6 周：选旗舰章

三个旗舰章不预设，用前三章的**真实数据**选。填 `progress/flagship-selection.yml`：

五个维度各 0–5 分：Attest 相关性 30% / 学习补强价值 25% / 跨章迁移 20% /
可形成强证据 15% / 可行性 10%。

**硬规则：每个子分必须引用真实数据**（章节成绩、实验结果、校准误差、Attest 需求）。
没有证据只能记 0——不能用"我对这章感兴趣"代替证据。

> 为什么是第 6 周而不是原方案的第 4 周：按 18 周节奏，第 4 周只完成 1.5 章，
> 数据不足以支撑选择。第 6 周你有三章完整数据，包括**校准误差**——
> 它会告诉你哪个维度是你的真实短板，而不是你以为的短板。

## 5.3 第 12 周：中期复盘

- Attest 到 v2.5，用前五章数据做 Judge 校准。**这是全程最关键的一次集成**
- 重算旗舰候选分。下降 ≥15 分、预计投入超预算、或已积压两章 → 替换或缩减
- 看校准误差趋势。如果它没有下降，说明你的自我评估能力没有改善，这比分数低更值得警惕

## 5.4 落后了怎么办

**不要延长周期，要降级范围。** 按优先级砍：

| 砍什么 | 保什么 | 影响 |
| --- | --- | --- |
| 1. 可选里程碑（v2.8 / v3+voice / v3+panel） | 十章证据 | 无（本来就是可选） |
| 2. 旗舰实验从 3 个减到 1–2 个 | 十章 done | 金 → 银 |
| 3. 4 章降为"最小验证实验"（跑通基线 + 1 个变量，不做完整指标矩阵） | 十章笔记 + 测试 + 答辩 | 银 → 铜 |
| 4. 最后才考虑跳过某章 | — | 破坏跨章迁移，尽量避免 |

**永远不砍的两样**：答辩（防 AI 代写）和间隔复习（防学完就忘）。
砍掉这两个，剩下的努力会全部作废。

# 第六部分 · 常见问题

**Q：书稿和实验在哪？**
本仓库默认放在 `ai-agent-book/` 内，`curriculum.yml` 的 `meta.book_repo: ".."` 指向它。
移到别处改这一个字段。

**Q：`check` 全是红的，是不是我做错了？**
不是。草稿状态下就该是红的，它是待办清单。全绿了才去 `grade`。

**Q：`grade` 提示未实现？**
对，那是第 1 章的里程碑（v0），由你实现。设计 brief 见 §4.3。

**Q：成本会不会失控？**
`.env` 里 `ATTEST_BUDGET_CNY=60` 是硬护栏，累计超过就拒绝调用。
当前配置（DeepSeek-V3 / 腾讯 LKEAP）实测单次 ping 0.000026 元，
全书约 90 次真实调用，预计总成本远低于 60 元。
流水在 `progress/llm-usage.jsonl`，按 `tag` 可以看每章花了多少。

**Q：可以换模型吗？**
可以，任何 OpenAI 兼容端点，改 `.env` 的三个 `LLM_*` 即可。
但注意：**换 Judge 模型后要回放校准集**（v2.5 之后），否则历史分数不可比。

**Q：笔记要不要提交到 GitHub？**
证据全部 `git commit` 是对的（版本化就是学习轨迹）。
但**仓库建议保持私有**，只把过了发布门的 `article.md` 单独发出去。
理由见 §2.5——知道会被公开，你写笔记时就不会诚实了。

**Q：第 7 章没有 GPU 怎么办？**
`report.md` 里已经写好三条路径。最推荐：租按小时 GPU（2–4 元/小时，
本实验 3 小时内完成，总成本 <15 元）走 P2 路径，用 Qwen2.5-0.5B 做 LoRA SFT。
硬要求只有一条：**真实的前向、反向、参数更新 + 训练前后同一评估**。

**Q：什么时候算真的学完了？**
不是十章都 `done`，而是：D+21 复习时你还能把关键概念迁移到新场景，
并且校准误差是收敛的——你既会，也知道自己会。
