## 0. 这份文档是什么

本目录下已有一套同事编写的方案（`README.md`、`learning-system-design.md`、`chapter-learning-requirements.md`、`chapter-assessment-blueprints.md`、`artifact-templates.md`、`implementation-plan.md`，约 10 万字）。

本文档做三件事：

1. **评估**那套方案哪些该保留、哪些必须替换，并给出可核实的依据；
2. **给出最优方案**：学习路线、逐章要求、监督与评估系统设计；
3. **回答"基于 GitHub 维护是否合适"**，并给出产品化路径。

本文档是自足的——只读这一份就能开始第一周。同事文档中仍然有效的部分（主要是逐章目标、成果模板）会明确标注为"直接复用"，不重复抄写。

## 1. 对同事方案的评估

### 1.1 一句话结论

**学习设计部分是优秀的，监督系统部分是过度设计的，两者应该拆开。**

同事把"如何证明自己真的学会了"这个问题想得很透——证据优先、四维评分、确定性检查与语义评分分离、个性化答辩、间隔复习保持率，这些都是真知灼见。问题出在实现载体：为了在 GitHub Actions 上做到"不可伪造"，引入了 Ed25519 签名、digest-pinned 镜像锁、无检出 Judge、tar 白名单、canonical input hash、原子预算账本、fail-closed 目标映射——这是**供应链安全级别的工程**，而真实场景是**一个人、学一本书、每周几小时**。

### 1.2 应当完整保留的部分（6 项）

| # | 保留项 | 为什么对 |
|---|---|---|
| 1 | **证据优先原则**："我理解了"不是证据，必须有可复现结果、基线对照、失败归因 | 这是整套方案的地基，也是它区别于"读书打卡"的根本 |
| 2 | **四维评分**：概念 25 / 场景与代码 30 / 实验证据 25 / 费曼讲解与反思 20 | 权重分配合理，"场景与代码"占最高分是对的——工程书的掌握度就体现在迁移能力 |
| 3 | **确定性检查与 LLM 评分分离**，且"基础设施错误不降低学习分数" | 这是很成熟的判断。没有这条，一次 API 超时就会污染学习数据 |
| 4 | **个性化答辩**：Judge 针对你本人的提交生成追问 | **这是全套方案里唯一真正能防住"AI 代写"的机制**，必须保留并强化（见 §5.1） |
| 5 | **间隔复习 D+2 / D+7 / D+21 + 保持率公式** | 直接对应"学完就忘"这个最大的实际失效模式 |
| 6 | **逐章学习要求**（`chapter-learning-requirements.md` 的目标、必答问题、通过标准） | 这是同事文档中价值最高的一份。必答问题是针对本书正文提出的真问题，不是通用套话，**本方案直接复用**（见 §4） |

同时保留一个反向判断：**不把提交次数、代码行数、在线时长作为核心 KPI**。这条写得很好。

### 1.3 必须替换的部分（8 项）

#### P1 · 整个实施计划是悬空的

`implementation-plan.md` 声称"五个可独立构建和验收的子系统"，链接到 `./plans/01-evidence-foundation.md` 至 `./plans/05-final-certification.md`。**这五份文件全部不存在。** `learning/`、`capstone/`、`progress/` 目录不存在，`.github/workflows/` 下只有仓库自带的 5 个流程，没有任何学习相关的。

也就是说：目前是 **约 10 万字规范 + 0 行可执行代码**。而 `week-01-quickstart.md` 里已经在教你执行 `agent-book-learn init-chapter 1` 这类根本不存在的命令。规范与实现的比例严重失衡，这本身就是一个危险信号——规范写到这个密度还没有一行代码验证过，说明其中相当一部分约束从未经受可行性检验。

#### P2 · 工程量倒挂：监督系统比学习本身还大

按同事方案自己的预算表，12 周 × 7 小时 = **84 小时，全部用于学习，实施监督系统的时间是 0**。

而要实现的东西包括：Ed25519 签名与验签、digest-pinned 容器镜像 lock、无仓库检出的 Judge job、严格 tar 白名单、提交绑定的 canonical input hash、原子预算账本、类型化 fail-closed 目标映射、受信发布器、两阶段 Judge 绑定协议、Web Demo 的 CSRF/Origin/Host/CORS 防护、并发单飞、原子状态写入、以及五个子系统各自的 TDD 测试套件。

保守估计 **150–300 小时**。这不是"学习之余顺手搭一下"能完成的，它会挤掉学习本身。

#### P3 · 威胁模型错配

签名、防篡改、fail-closed 的目的是**防止学习者作弊**。但学习者 = 你自己 = 系统的唯一用户和唯一受益人。为了防自己伪造分数而引入私钥签名，是拿一个高成本机制去解决一个不存在的问题。

更关键的是：**真正的作弊风险不是"改分数文件"，而是"让 AI 代写笔记和文章"。** 而签名机制对此完全无效——AI 写的内容照样能被合法签名，哈希照样对得上。方案里唯一真正针对这个风险的机制是个性化答辩，它应该被扩大，而不是被埋在一堆密码学仪式里。

#### P4 · 时间预算与真实内容量不匹配（有量化依据）

实测十章正文的中文字符数：

| 章 | 中文字符 | 单次通读（400 字/分钟） |
|---:|---:|---:|
| 1 | 18,911 | 47 分钟 |
| 2 | 33,978 | 85 分钟 |
| 3 | 27,936 | 70 分钟 |
| 4 | 27,814 | 70 分钟 |
| 5 | 29,640 | 74 分钟 |
| 6 | 26,513 | 66 分钟 |
| 7 | 37,344 | **93 分钟** |
| 8 | 15,735 | 39 分钟 |
| 9 | 23,445 | 59 分钟 |
| 10 | 30,261 | 76 分钟 |
| **合计** | **271,577** | **11.3 小时** |

同事方案给"阅读与批注 1.5 小时/章"。对第 2、7、10 章，1.5 小时**只够勉强通读一遍**，而方案同时要求"第一次快速通读 + 第二次围绕问题精读 + 完成概念图"。这做不到。

同样偏紧的还有"代码与对照实验 2 小时"——第 1 章要求跑三组消融、记录成功率/步数/延迟/token/异常循环五类指标、保存成功与失败轨迹。在真实 API 延迟（每个 task 数十秒到数分钟）下，光是跑完就不止 2 小时。

**结论：7 小时/周是理想值，真实需求约 10–12 小时/周。** 方案要么加时间，要么减范围，不能两个都不动。

#### P5 · 判定规则过度复杂

"唯一判定优先级"有 8 条，状态有 6 种（`excellent`/`passed`/`needs_revision`/`needs_review`/`failed`/`evaluation_error`），外加两阶段 Judge 绑定、`issued_for_input_hash` 回显校验、`latest-evaluation-error.json` 错误旁路、不可拆分的原子签名对。

单是把这套规则实现正确并做到测试覆盖，就是一个中等规模项目。而它解决的问题——"这章算不算过"——在单人场景下用**一张表 + 三条判定**就够了（见 §5.5）。

#### P6 · 答辩流程的人体工学很差

按 `week-01-quickstart.md` 的流程，完成一次答辩需要：

```
commit → push → 等 Actions（排队+冷启动+装依赖+调 LLM）→ git pull
→ 从签名 JSON 里手工原样复制 question_id / issued_for_input_hash / question
→ 填进 strict YAML front matter（正文只能是 # Defense）
→ commit → push → 等 Actions → git pull
```

**两次 push、两次等 CI、一次手工哈希搬运。** 十章就是 20 次往返。这把"学习反馈"变成了"和 CI 打架"。而答辩本身的价值——即时、追问、无法预先准备——恰恰要求它是**对话式**的。

#### P7 · 成本控制机制的复杂度远超它控制的金额

方案设计了：原子预算账本、跨章节共享预算、重试不得重置上限、输入价/输出价必须显式配置为正数、内容哈希缓存、长文结构化分段后聚合、同分支新提交取消旧评估。

而实际成本量级：每章 Judge 调用约 6–8 次，十章约 60–80 次；用 GLM / Kimi / DeepSeek 这类国产模型，全书总成本在**数十元人民币**。为了控制几十块钱而建一套原子预算账本，投入产出比是负的。

#### P8 · 硬门设置会让方案"一票否决"

方案要求：十章全部 `passed`（≥80）+ 十篇文章全过发布门 + 三个旗舰全过 + Demo ≥80 + 总复盘 ≥80 + 最终总分 ≥85，**任何硬门失败都不能被高分抵消**。

单人自学场景下这意味着：只要第 7 章卡住（很可能——它需要 GPU），整个 12 周判定为失败。这种全有或全无的设计会在中途制造放弃点，而不是激励完成。

### 1.4 已核实的三处实验硬伤

这三处不是意见分歧，是方案与实际代码仓库的事实冲突：

| # | 位置 | 冲突 |
|---|---|---|
| **A** | 第 7 章 | 方案写"**强制默认基线**是 `chapter7/continued-pretraining/`"，同时要求"对**不超过 0.6B–1.5B** 的小模型进行 50–200 步真实训练"。但该项目 README 明确：基座是 **Mistral 7B v0.3**，4-bit 量化，**需要约 24GB 显存的 NVIDIA GPU（RTX 4090）**。两个要求无法同时满足，且没有 24GB 卡的人直接被卡死在第 7 章 |
| **B** | 第 6 章 | 方案要求"构建或使用**不少于 20 个任务**"。默认实验 `chapter6/public-health-reporting-eval` README 明确写着 **五个确定性任务**（阳性率、报告完整性、周期趋势、数据质量、缺货审查）。要凑到 20 个必须自己扩数据集和验证器，这部分工作量**没有出现在任何时间预算里** |
| **C** | 第 9 章 | 默认实验 `chapter9/streaming-speech` README 明确："**必须使用 OpenAI 直连 Key**（`whisper-1` / `tts-1`），OpenRouter 只处理 chat completions，无音频端点，无法回退。"方案对此只字未提。虽有 `--offline` 模式，但离线模式下没有真实 ASR 延迟数据，方案要求的"首个可用文本延迟 / 最终延迟"指标就是空的 |

修正方案见 §4 对应章节。

### 1.5 直接回答："基于 GitHub 来维护合适吗？"

**你的判断是对的，但要分两层看：Git 作为存储层是对的，GitHub Actions 作为运行时是错的。**

#### Git 应该保留（作为存储层）

- 证据天然版本化，`git log` 就是学习轨迹，`git diff` 就是认知变化，这比任何打卡记录都真实；
- 离线可用，数据自持；
- 防篡改是免费副作用——改历史会留痕，根本不需要额外签名。

#### GitHub Actions 不该作为运行时（5 个具体理由）

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **反馈延迟致命** | 写完一段笔记想问"我这样理解对吗"，需要 commit → push → 排队 → 冷启动 → 装依赖 → 调 LLM → pull，乐观 3–8 分钟，装 ML 依赖时 15 分钟起。而学习最需要的是**秒级**反馈。没人会为了一个问题提交一次 commit |
| 2 | **公开 = 自毁核心价值** | 方案默认"公开 GitHub 仓库"+"公开看板展示各维度分数热力图"。这意味着你学习早期的低分、错误认知、"我不理解 X"全部永久公开。而这套方案最大的价值来源恰恰是**诚实记录自己不懂的地方**。一旦知道会被公开，笔记的诚实度必然下降——**这是一个自我毁灭的设计** |
| 3 | **网络与配额现实** | 国内本地 push/pull GitHub 本身就不稳定；私有仓库 Actions 有免费分钟数上限；Actions 排队、限额、平台策略变更都不在你的控制内 |
| 4 | **逻辑锁死在 YAML** | 核心评估逻辑散落在 workflow YAML + composite action 里，无法在本地跑、无法单元测试、无法复用到 Web/桌面/小程序 |
| 5 | **不是产品形态** | 你提到想把系统泛化成产品。GitHub-native 要求每个用户都有 GitHub 账号、会用 git、能配 Actions Secrets、能读 workflow 日志——目标用户被压缩到"熟练开发者"这一小群，且是这群人里最不需要监督的一群 |

#### 正确的分层

```
展示层（可选，公开）   GitHub Pages / 博客  ← 只放通过发布门的成果，脱敏
      ↑ 手动或定时同步
存储层（主，私有）      本地 Git 仓库        ← 全部学习证据，含不体面的部分
      ↑ 秒级读写
运行时（主）           本地 CLI / 库         ← 检查、出题、评分、答辩，全部本地
      ↑ 可选
CI（可选，非关键路径）  GitHub Actions        ← 每周一次回归 + 看板构建，挂了不影响学习
```

一句话：**Git 是账本，不是流水线。**

## 2. 最优方案总览

### 2.1 三个设计判断

**判断一：本地优先，CI 可选。**
所有反馈路径必须是秒级、离线可跑、不依赖任何外部服务可用性。CI 只做"每周回归 + 生成公开看板"这类非关键路径的事，挂掉不影响学习。

**判断二：监督系统就是综合 Demo，不做两个东西。**
同事方案把"监督系统"（Python CLI + Actions）和"综合 Demo"（`capstone/learning-lab`）分开做，两者功能高度重叠，是重复工程。

本方案合并：**你要建的监督系统，本身就是用这本书的技术建的，它就是你的综合 Demo。** 每学完一章，就把这一章的能力装进这个你每天都在用的系统里。用不用得上、好不好用，是对"是否真的学会"最诚实的检验（详见 §6）。

**判断三：防的是"AI 代写"和"学完就忘"，不是"篡改分数"。**
安全机制的强度按真实威胁配置，不按想象中的威胁配置（详见 §5.1）。

### 2.2 周期与强度：两个方案，选一个

按 §1.3-P4 的实测数据重算：

| | **A · 稳健版（推荐）** | **B · 高强度版** |
|---|---|---|
| 周期 | **18 周** | **12 周** |
| 每周投入 | 7–8 小时 | 11–13 小时 |
| 节奏 | 每章 1.5 周 × 10 = 15 周 + 综合 3 周 | 每章 1 周 × 10 + 综合 2 周 |
| 总投入 | ≈ 130 小时 | ≈ 145 小时 |
| 适合 | 有本职工作、想真正吃透 | 有整块时间、能连续投入 |

还有一个降级选项，用于时间被压缩时**保住核心而不是全线崩溃**：

**C · 12 周轻量版（84 小时）**：十章全部完成笔记 + 测试 + 答辩，但只有 6 章做完整对照实验，另外 4 章做"最小验证实验"（跑通基线 + 改一个变量，不做完整指标矩阵）。哪 4 章降级，在第 4 周按 §5.6 的实测数据决定。

**默认推荐 A。** 每章标准预算：

| 活动 | 时间 | 产出 |
|---|---:|---|
| 通读 + 标记疑问 | 1.0 h | 疑问清单 |
| 精读 + 概念图 + 回答必答问题 | 1.5 h | `notes.md` |
| 实验：跑基线 + 改变量 + 记录 | 3.0 h | `lab/`、`summary.json`、成功与失败轨迹 |
| 实验报告 | 1.0 h | `report.md` |
| 文章 | 1.5 h | `article.md` |
| 测试 + 答辩 | 1.0 h | `quiz.md`、`defense.md` |
| 把本章能力装进系统 | 1.0 h | 系统 vN 增量 |
| 复习到期项 + 周复盘 | 1.0 h | `review`、`retro.md` |
| **合计** | **11 h / 章** | 分摊到 1.5 周 = 7.3 h/周 |

### 2.3 最终成果清单

| 成果 | 数量 | 说明 |
|---|---:|---|
| 逐章结构化笔记 | 10 | 私有，允许写"我不懂" |

## 3. 每章的标准学习循环（五步）

```
① 定标   attest start ch0N
         → 打印本章目标、必答问题、实验要求、与前置章节的连接点
         → 自动把默认实验快照到 evidence/ch0N/lab/<项目名>/

② 学做   通读 → 精读 → 概念图 → 跑基线 → 改一个变量 → 记录
         → 全程本地，随时 attest check 拿秒级结构反馈

③ 表达   写 report.md 和 article.md
         → attest check 校验：报告里的每个数字必须能在 summary.json 里找到

④ 验收   attest quiz  → 生成本章测试（基于正文 + 你的笔记 + 你的实验 + 历史错题）
         attest grade → 四维评分
         attest defend→ 终端里当场答辩，2 个针对你本人提交的追问，即时评分

⑤ 沉淀   attest review 排期 D+2/D+7/D+21
         attest ship   把本章能力装进 Attest 自身（Demo 增量）
         周复盘
```

关键区别：**②③ 两步随时可以调 `check` 拿反馈，不需要提交任何东西。** ④ 的答辩是终端里的一次对话，不是两次 push。

## 4. 逐章学习要求

> **复用说明**：以下每章的「学习目标」与「必答问题」直接沿用同事的 [`chapter-learning-requirements.md`](./chapter-learning-requirements.md)——那份文档在这一层做得很好，问题都是针对本书正文的真问题，重写只会变差。本节在其基础上补充三件事：**① 实测阅读时长；② 默认实验的可行性修正（第 6/7/9 章有实质改动）；③ 本章能力如何装进 Attest 系统**。

### 统一完成标准（每章）

1. 六类产出齐套：`notes.md` / `lab/` / `report.md` / `article.md` / `quiz.md` / `defense.md`
2. `attest check` 全绿（无占位符、证据可定位、复现命令可执行、报告数字与 `summary.json` 一致、无密钥泄漏）
3. 实验至少含一个固定基线 + 一个主要变量，保存一条成功轨迹和一条失败轨迹
4. 文章有一个可争辩的独立主张，且至少引用一个自己的实验数字
5. 章节测试总分 ≥ 80，任一维度 ≥ 该维度满分的 60%
6. 答辩完成（两个追问均已作答并评分）

### 第 7 章 · 模型后训练 ⚠️ 有重大修正

| | |
|---|---|
| 正文 | **37,344 字（全书最长）** · 建议阅读 **3.0 h** |
| 原方案默认实验 | ~~`chapter7/continued-pretraining/`（强制）~~ ❌ |

> **修正 A**：原方案把 `chapter7/continued-pretraining/` 定为"强制默认基线"，同时要求"不超过 0.6B–1.5B 的小模型"。但该项目 README 明确：基座 **Mistral 7B v0.3**，4-bit 量化，**需约 24GB 显存 NVIDIA GPU（RTX 4090）**。二者不可能同时成立，且无 24GB 卡的人会被硬卡在这里。
>
> **本方案改为按算力分三条路径，硬要求不变。**

**不变的硬要求**（三条路径都必须满足）：

- 有**真实的前向、反向、参数更新**（不接受伪代码、不接受只贴训练日志样例）；
- **训练前后使用同一套评估**，同时报告**目标能力**和**能力保留集**；
- 记录：数据来源与过滤、学习率/batch/步数/随机种子、训练时长与显存、训练 loss、目标任务变化、保留集变化、**至少一个失败或退化案例**。

**三条路径**：

| 路径 | 条件 | 做法 |
|---|---|---|
| **P1 · 有 ≥24GB GPU** | RTX 4090 / A100 等 | 沿用 [`chapter7/continued-pretraining/`](../chapter7/continued-pretraining/) 原路径（Mistral-7B + LoRA + 韩语续训 → SFT），它自带三阶段对比脚本和灾难性遗忘的处理，是最完整的一条 |
| **P2 · 有 8–16GB GPU 或云 Notebook（推荐大多数人）** | RTX 3060/4060 / Colab / AutoDL 按小时 | 换基座为 **Qwen2.5-0.5B 或 1.5B**，做 LoRA SFT，50–200 步。训练数据用 [`chapter7/cot-distillation/`](../chapter7/cot-distillation/) 生成并做规则过滤（它自带 SFT 数据生成与验证器）。目标能力选一个**可自动验证**的窄任务（如固定格式的工具调用生成），保留集用通用问答 20 题 |
| **P3 · 完全无 GPU** | 只有 CPU | 用 [`chapter7/MiniMind-pretrain/`](../chapter7/MiniMind-pretrain/) 训一个极小模型（几十 M 参数），CPU 上可跑通完整的预训练→SFT 流程。任务效果会很差，但**参数更新是真实的**，且能亲手看到 loss 下降与灾难性遗忘。或者：租按小时 GPU（约 2–4 元/小时，本实验 3 小时内可完成，总成本 &lt;15 元，**强烈建议走这条而不是 P3**） |

**必答问题**：
1. 何时应从 SFT 切换到 RL？
2. 如何决定一项能力进入参数还是上下文？
3. Agentic 轨迹中哪些 token 应学习，哪些不应学习？
4. 多轮任务的奖励如何归因？
5. 如何同时提升目标能力并保护通用能力？

**通过标准**：有真实训练代码路径；训练前后同一评估；同时报告目标与保留能力；**不用训练 loss 代替任务效果**；能识别评估泄漏与 reward hacking 风险。

**文章命题**：《能力应该写进权重，还是留在上下文、Skill 与程序里？》

**装进 Attest**：**v2.8（可选）— 小模型预筛**。用一个 0.5B 模型做便宜的第一道过滤（判断"是否是占位内容""是否空泛套话"），只有通过预筛的才送给大模型评分。这正好是本章核心问题的真实取舍：**这项能力该放进参数（微调小模型）还是放进上下文（给大模型写 prompt）？** 你可以两条都做，然后用第 6 章的方法比较。

## 5. 监督与评估系统：Attest（明证）

### 5.1 威胁模型：真正要防什么

先明确要防的失效模式，再配置机制强度。这是与同事方案分歧最大的地方。

| # | 真实失效模式 | 发生概率 | 有效对策 | 同事方案的对策 |
|---|---|---|---|---|
| **T1** | **AI 代写笔记与文章**（看起来完美，其实没进脑子） | **极高** | ① 个性化答辩（针对你本人提交的追问，无法预先准备）② 语音作答（第 9 章后启用）③ 要求引用**自己实验的具体数字** ④ D+21 复述——AI 写的东西 3 周后你解释不了 | 有答辩机制 ✅ 但被埋在签名/哈希流程里，且只有 1 个问题 |
| **T2** | **实验只跑通不分析**（有 `summary.json`，没有结论） | **高** | 确定性检查：报告里出现的每个数字，必须能在 `summary.json` 里定位到（约 40 行代码） | 有类似要求 ✅ |
| **T3** | **学完就忘** | **高** | D+2/D+7/D+21 间隔复习 + 保持率 | 有 ✅ |
| **T4** | **自欺**（自评远高于真实水平） | **中高** | **校准误差**：每章先自评，再看 Judge 评分，记录差值与趋势 | ❌ 无此机制 |
| **T5** | **进度虚高**（读了但没做实验） | 中 | 状态由证据齐套度决定，不由阅读进度决定 | 有 ✅ |
| **T6** | 篡改分数文件 | **≈ 0**（你是唯一用户） | Git 历史（免费） | Ed25519 签名 + 哈希绑定 + 受信发布器 ❌ 过度 |
| **T7** | 学习者代码攻击评估系统 | **≈ 0**（代码是你自己写的） | 常识 | 无网络无密钥沙箱 + tar 白名单 + 无检出 Judge ❌ 过度 |

**T4「校准误差」是同事方案完全缺失、但价值很高的一个指标**：它衡量的是"你知不知道自己会不会"。元认知准确度比分数本身更能预测长期学习效果，而且它是一个天然的产品化差异点——没有任何学习产品在测这个。

**结论**：把 T6/T7 的全部密码学机制删掉，把省下的工程量投到 T1（答辩加强到 2 问 + 语音）和 T4（校准误差）上。

### 5.2 三层评估

```
第 1 层  确定性检查（本地，<2 秒，零成本，随时可跑）
         ├─ 六类产出齐套、必需小节非空、无 TODO/待填写/占位符
         ├─ 证据索引的每条 path+location 可解析到真实位置
         ├─ report.md / article.md 里的数字能在 summary.json 中找到  ← 防 T2
         ├─ reproduce 命令可执行、退出码为 0、产物一致       ← 第 5 章能力
         └─ 密钥与隐私扫描（这个真有用：防 API Key 进仓库）
         失败 → 直接 needs_work，不调用 LLM（明确且省钱）

第 2 层  语义评分（本地调 API，约 30 秒，约 0.3 元/章）
         四维打分 + 逐条理由 + 证据引用 + 与自评的差值
         记录 rubric 版本、judge 模型、输入哈希（用于事后核对，不签名）

第 3 层  个性化答辩（终端对话，约 10 分钟，你在场）
         系统读你的提交 → 生成 2 个针对性追问 → 你当场作答 → 即时评分
         问题必须锚定你的具体主张/代码选择/实验数字，不能是通用问题
```

关键设计：**第 1 层随时可跑、零成本**，所以你会在写作过程中反复用它，而不是写完才发现结构不对。这是本地优先带来的最大收益。

### 5.3 数据模型：三个可泛化抽象

系统的可产品化程度，取决于内核抽象是否与"AI Agent Book"无关。三个抽象：

```
attest/
├── curriculum.yml            # ① 课程规格 —— 换本书只换这个文件
│     units:
│       - id: ch01
│         title: AI Agent 基础
│         source: book/chapter1.md
│         objectives: [...]
│         must_answer: [...]        # 必答问题
│         default_lab: chapter1/context
│         rubric: rubric/engineering-book.yml
│         connects_to: []
│
├── rubrics/                  # ② 评分卡 —— 与学科无关，可复用可分享
│     engineering-book.yml:
│       dimensions:
│         - {id: concepts,    weight: 25, anchors: {...}, anti_patterns: [...]}
│         - {id: scenario,    weight: 30, ...}
│         - {id: experiment,  weight: 25, ...}
│         - {id: teachback,   weight: 20, ...}
│
└── evidence/ch01/            # ③ 证据包 —— 目录约定，与内容无关
      notes.md  report.md  article.md
      lab/{src,results/summary.json,reproduce.json,tests}
      quiz.md  defense.md  retro.md
      .attest/state.json     # 状态、分数、自评、错题、复习排期
```

**任何一本技术书、任何一门课程，只需要填 `curriculum.yml` 和选一张 `rubric` 就能接入。** 这是产品化的地基（详见 §7）。

### 5.4 命令集

|---|---|---|
| `attest init <curriculum.yml>` | 秒 | 初始化工作区 |
| `attest start ch07` | 秒 | 打印本章目标/必答问题/实验要求/前置连接；把 `default_lab` 快照到 `evidence/ch07/lab/<项目名>/` 并记录来源 |

| `attest grade ch07` | ~30 s | 第 2 层四维评分，输出分数 + 理由 + 证据 + **校准误差** |

### 5.5 评分与门控（简化版）

**四维权重不变**（沿用同事方案，这部分是对的）：

| 维度 | 权重 |
|---|---:|
| 概念理解 | 25 |
| 场景与代码 | 30 |
| 实验证据 | 25 |
| 费曼讲解与反思（含答辩） | 20 |

**状态只有 4 个**（不是 6 个）：

| 状态 | 条件 |
|---|---|
| `draft` | 起草中 |
| `needs_work` | 见下方判定 |
| `done` | 全部通过 |
| `done*`（优秀） | `done` 且总分 ≥ 90 → 自动进入旗舰候选池 |

**判定只有 3 条**（不是 8 条），按顺序：

1. 第 1 层确定性检查失败 → `needs_work`（**不调用 LLM**）
2. 答辩未完成 → `needs_work`
3. 总分 ≥ 80 **且** 每维 ≥ 该维 60% → `done`；否则 `needs_work`

**基础设施错误单独处理**（沿用同事方案的正确判断）：API 超时、依赖失败、Judge 返回非法 JSON → 不写分数，只写 `last_error`，保留上一次有效结果。看板同时显示"最近有效成绩"与"当前故障"。

**门槛也调整**（修掉 §1.3-P8 的一票否决问题）：

| 完成级别 | 条件 |
|---|---|
| 🥉 **铜**（基本达成） | 十章证据齐套，八章以上 `done`，平均分 ≥ 75 |
| 🥈 **银**（推荐目标） | 十章全部 `done`，平均分 ≥ 80，十篇文章过发布门，Attest 到 v2 |
| 🥇 **金**（完整达成） | 银 + 3 个旗舰实验 + Attest 到 v3 + 总复盘 + D+21 保持率 ≥ 0.8 |

**旗舰实验和 Demo 是加分项，不是硬门。** 这样第 7 章卡住不会导致整个方案判定失败——你仍然能拿到银牌，并且清楚地知道差在哪。

### 5.6 指标体系

看板展示（**加粗为同事方案没有、但更有价值的指标**）：

| 指标 | 定义 | 为什么看 |
|---|---|---|
| 章节状态 | 10 章 draft/needs_work/done | 覆盖度 |
| 四维雷达 + 趋势 | 每章四维分数 | 找系统性短板 |
| **校准误差** | `mean(\|自评 − Judge评\|)` 及趋势 | **你知不知道自己会不会**。应随周次下降 |
| **保持率** | D+7、D+21 得分 ÷ 首评得分 | ≥0.9 良好；0.75–0.89 安排复习；&lt;0.75 回补学队列 |
| **证据密度** | 文章中可定位引用数 ÷ 核心主张数 | 衡量"有没有真拿数据说话" |
| **复现率** | `attest check` 一次通过的章节比例 | 工程严谨度 |
| **返工轮数** | needs_work → done 的平均轮数 | 下降说明质量前置了 |
| 累计成本 | token 与费用 | 预算感 |

**明确不采纳**（沿用同事的正确判断）：commit 数、代码行数、在线时长。这些容易被优化，且不代表学习质量。

### 5.7 间隔复习

沿用同事方案的设计，改为本地执行：

- **D+2**：3 个概念辨析，每题需说明一个常见误解（约 10 分钟）
- **D+7**：1 个新工程场景，必须调用本章 ≥2 个概念（约 15 分钟）
- **D+21**：1 个跨章迁移题，由系统根据你**已学的后续章节**生成（约 20 分钟）

保持率公式：`保持率 = 间隔测试得分 / 首次通过得分`

错题进 `review-queue`，字段：错误概念 / 错误类型 / 原答案 / 反馈 / 关联章节 / 下次复习时间 / 连续正确次数。**同一错误连续出现两次时，不再生成相似题，而是要求补一个最小实验或反例解释**——这条设计很好，保留。

### 5.8 成本

| 项 | 每章 | 全书（10 章） |
|---|---:|---:|
| 出题 | 1 次调用 | 10 |
| 评分 | 1–2 次 | 15 |
| 答辩（2 问） | 2 次 | 20 |
| 复习题生成 | 3 次（小） | 30 |
| 修订重评 | ~1.5 次 | 15 |
| **合计** | ~8 次 | **~90 次调用** |

## 6. 监督系统 = 综合 Demo

这是本方案与同事方案最大的结构性差异，也是最能省工程量、同时提高学习质量的一个决定。

**同事方案**：监督系统（Python CLI + GitHub Actions）和综合 Demo（`capstone/learning-lab`）是两个东西，功能高度重叠，要分别实现、分别测试、分别验收。

**本方案**：合并为一个。你要建的监督系统，本身就用这本书的技术建；每学完一章，把这一章的能力装进这个你**每天都在用**的系统。

为什么这是最好的检验：**一个你自己每天用的工具，好不好用你骗不了自己。** 跑一个 demo 项目跑通了，不代表你能用它解决问题；但如果第 3 章的检索让你的 Judge 引用更准了、第 6 章的校准让你开始相信分数了、第 8 章的进化闭环真的改进了 rubric——那是没法作假的掌握。

### 版本路线

| 版本 | 时点 | 内容 | 用上的章节能力 |
|---|---|---|---|
| **v0** | ch1 后 | Agent 循环骨架：读证据（工具）→ 调 LLM 判分（模型）→ 写结果（工具）；终止条件、重试、预算 | 第 1 章 Harness |
| **v0.5** | ch2 后 | 分层上下文：稳定前缀（rubric + 课程规格）+ 动态部分（本章证据）；实测缓存命中的成本下降 | 第 2 章 KV Cache / 稳定前缀 |
| **v1** | ch3 后 | 证据检索：书稿 + 十章笔记建索引，Judge 打分**必须引用原文位置** | 第 3 章 混合检索 + 重排 |
| **v1.5** | ch4 后 | 工具化：check/quiz/grade/defend 变成工具 + 主动发现；对比全量注入 vs 按需发现的真实 token | 第 4 章 工具设计 / 主动发现 |
| **v2** | ch5 后 | 复现检查器：沙箱内执行 reproduce、跑测试、比对 `summary.json` | 第 5 章 生成—执行—验证闭环 |
| **v2.5** ★ | ch6 后 | **Judge 校准**：用前五章历史评分建校准集，测自洽性、位置偏差、长度偏差。**系统从"玩具"变"可信"** | 第 6 章 评估方法论（100% 用上） |
| **v2.8** | ch7 后（可选） | 小模型预筛：0.5B 判"是否占位/空泛"，大模型只处理通过预筛的 | 第 7 章 能力放参数还是放上下文 |
| **v3** | ch8 后 | 自我进化闭环：从历史评分轨迹自动提 rubric/prompt 改进 → 校准集验证 → 发布或回滚；可信根不可自动修改 | 第 8 章 持续进化 |
| **可选** | ch9 后 | 语音答辩：口头讲解 → ASR → 评分。更快、更难代写 | 第 9 章 流式语音 |
| **可选** | ch10 后 | 多 Judge 独立打分 + 分歧仲裁，**等 token 预算**下对比单 Judge 三次取均值 | 第 10 章 多 Agent 等预算对照 |

### 一个额外收益

到第 12 周，你手上会有一个**已经在真实场景连续运行 4 个月的 Agent 系统**，有完整的评估数据、校准记录、失败案例和演进历史。这比任何"周末做的 demo"都更有说服力——无论是用来写文章、做分享，还是作为产品原型。

## 7. 产品化路径

### 7.1 泛化内核

产品的价值不在"AI Agent Book"，在三个与内容无关的抽象（§5.3）：

| 抽象 | 换一门课要改什么 |
|---|---|
| **Curriculum Spec** | 换 `curriculum.yml`（单元、目标、必答问题、默认实践、rubric 引用） |
| **Rubric Card** | 从内置库选一张，或改权重与锚点 |
| **Evidence Bundle** | 不用改（目录约定与学科无关） |

引擎的六步（start → check → quiz → grade → defend → review）也与内容无关。

### 7.2 MVP 定位

**不要做成"学习打卡"或"AI 笔记"**——这两个赛道拥挤且没有壁垒。

真正的定位是：**"学完一门课，给你一份可信的能力证明。"**

三个差异点，都是竞品没有的：

| # | 机制 | 解决的问题 |
|---|---|---|
| 1 | **证据绑定**：每个结论必须绑到可定位的证据（代码、数据、结果） | 让"看起来学会了"和"真的学会了"可区分 |
| 2 | **个性化答辩**：针对你本人的提交生成追问 | **让 AI 代写失效**——这是 2026 年所有学习产品的头号问题，几乎没人在正面解决 |
| 3 | **保持率复测**：D+7 / D+21 自动复测 | 让"学完就忘"暴露；也是唯一能证明"三个月后还会"的机制 |

再加一个元认知指标 **校准误差**（§5.6）作为独特卖点：市面上没有任何学习产品在测"你知不知道自己会不会"。

### 7.3 演进路线

| 阶段 | 形态 | 关键动作 |
|---|---|---|
| **P0**（本方案，4–6 周） | 个人 CLI + 本地看板 | 跟着学习进度自然长出来，同时是本书综合 Demo。**不要为了产品化提前做抽象** |
| **P1** | 课程包生态 | `curriculum.yml` 可分享。做 2–3 个别的课程包验证泛化性（比如另一本技术书、一门公开课）。**这一步是验证"内核真的与内容无关"的唯一方法** |
| **P2** | 多用户 Web | 证据存后端（Git 后端或对象存储），评估服务化。**团队视图**：Leader 看到的是团队学习质量与校准误差，而不是完课率 |
| **P3** | 企业内训 | 接内部文档/规范生成 curriculum，输出可审计的培训效果证明 |

**P3 是真正付费的场景。** 现在所有企业内训系统只能报"完课率"和"考试通过率"——前者毫无意义，后者可以背题库。没有任何一个能回答"这批人真的会了吗"。证据绑定 + 个性化答辩 + 保持率复测正好回答这个问题，而且输出的是可审计的证据链，符合培训部门要向上汇报的需求。

### 7.4 Git 在产品里的角色

**保留 Git 作为可选存储后端，并把它当作卖点**：

> 你的学习证据存在你自己的 Git 仓库里。产品倒闭了，数据还在，历史还能查。

这是对"数据自持"敏感的开发者/技术团队的真实吸引力，也是对 SaaS 锁定的天然回答。但它是**可选后端**，不是**必选运行时**——普通用户走托管存储，技术用户可以指向自己的仓库。

## 9. 从今天开始的前三天

不要先建系统。**先完成第 1 章的一次完整循环，再把这次循环里手工做的事自动化。** 这样每一行代码都有明确的用途。

**Day 1（2 h）· 跑起来**
1. 申请 API Key（推荐 GLM + Kimi 双备份，国内直连；如需 OpenAI 音频端点，第 9 章前再解决）
2. 建 `learning/`（**本地私有仓库，不 push 公开**），初始化 git
3. 跑通 `chapter1/context` 的一个 task，确认环境 OK
4. 手写 `attest/curriculum.yml` 的 ch01 条目（照 §5.3 的结构）

**Day 2（3 h）· 学第 1 章**
1. 通读第 1 章（18,911 字，约 47 分钟）+ 标记疑问
2. 精读 + 画概念图 + 回答 5 个必答问题 → `evidence/ch01/notes.md`
3. **先自评四维分数**写进 `.attest/state.json`（这是校准误差的第一个数据点）

**Day 3（3 h）· 实验 + 写第一段代码**
1. 跑三组上下文消融，保存 `summary.json` + 一条成功轨迹 + 一条失败轨迹
2. 写 `report.md`
3. **写 `attest check` 的 v0**——约 80 行 Python：检查必需小节存在且非空、无 `TODO/待填写`、`summary.json` 存在且是合法 JSON、`report.md` 里出现的数字能在 `summary.json` 里找到。跑它，让它报错，修到全绿

到第 3 天结束，你会有：一章真实证据 + 一个真的在用的工具 + 对"这套流程哪里别扭"的第一手判断。**后面所有系统设计都基于这个判断，而不是基于规范文档的想象。**
